# Code review

## P0 — The merge-request pipeline cannot currently be created

This is the immediate blocker.

`.node-job` defines `rules` for merge-request, branch, and tag pipelines. Most existing jobs inherit those rules.
`container:build` and `container:http-contract`, however, do not inherit them and define no rules of their own.
Meanwhile, `container:browser-contract` and `build` do run in MR pipelines and have hard `needs` dependencies on those
missing jobs.

The current MR pipeline fails before executing any job:

> `container:browser-contract` needs `container:build`, but `container:build` does not exist; `build` similarly needs
> `container:http-contract`. ([GitLab][1])

This follows GitLab's documented semantics: jobs without `rules` default to behavior equivalent to excluding
merge-request pipelines, while jobs explicitly configured for MR pipelines are included. GitLab recommends making the
producer and consumer rules consistent when a `needs` relationship is mandatory. ([GitLab Docs][2])

**Recommendation:** define one canonical pipeline-presence policy and reuse it for every mandatory job. I would use
`workflow: rules` to control which pipelines exist, plus a reusable job-rule definition where necessary. Do **not**
solve this with `needs: optional`: container verification is intended to be mandatory, so making the dependency optional
would weaken the contract rather than repair it.

**Behavior:** infrastructure-only; no website behavior change.

## P0 — `container:browser-contract` does not target the container

The job correctly declares:

```text
CONTAINER_BASE_URL=http://dibs:8080
```

and disables Playwright's local `webServer` when that variable exists. But `playwright.config.ts` still always sets:

```ts
baseURL: "http://127.0.0.1:4321";
```

The environment variable affects only whether Astro is started; it never changes `baseURL`.

Consequently, once the pipeline graph is repaired, the container browser job will try to access localhost without
starting the local Astro server rather than exercising `dibs:8080`.

This is especially important because the browser job is supposed to establish something the HTTP probe cannot: that
generated client-side islands actually hydrate and behave correctly.

**Recommendation:** make the target explicit:

```ts
const externalBaseUrl = process.env.CONTAINER_BASE_URL;

use: {
    baseURL: externalBaseUrl ?? "http://127.0.0.1:4321",
}

webServer: externalBaseUrl
    ? undefined
    : { /* Astro development server */ }
```

Even better, extract the environment selection into a tiny pure configuration function and test it with DDT:

- no external URL → local Astro server + localhost;
- external URL → specified URL + no local server.

Then reuse an existing behavioral Playwright test against the candidate OCI image instead of introducing a separate
Docker-specific browser semantics suite.

**Behavior:** behavior-preserving; repairs a false verification boundary.

## P1 — Production OCI aliases are published before the image passes its container contracts

`container:build` currently pushes the pipeline candidate, but on `main` it also immediately pushes the SHA alias; on
tags it additionally publishes SHA, Git tag, and package-version aliases. Only **after** that job completes are
`container:http-contract` and `container:browser-contract` executed.

The effective flow is:

```text
build
  │
  ├─ publish candidate
  ├─ publish SHA / release aliases
  │
  ▼
test candidate
```

That weakens the provenance guarantee: a durable release alias may already exist even if a downstream container-contract
job subsequently fails.

For a project explicitly concerned with reproducible research artifacts and provenance, the stronger contract should be:

```text
build candidate
      │
      ▼
candidate digest
      │
      ├─ HTTP contract
      ├─ browser contract
      └─ runtime/image contract
              │
              ▼
       promote same digest
       to durable aliases
```

**Recommendation:** `container:build` should publish **only a pipeline-scoped candidate** and persist its manifest
digest. Add a separate `container:publish` job after all container verification jobs. It should promote/tag that exact
digest without rebuilding it.

That also makes “what was tested?” answerable with one immutable identifier.

**Behavior:** packaging/provenance improvement only.

## P1 — The OCI provenance currently points to the wrong repository

The Dockerfile records:

```text
org.opencontainers.image.source="https://github.com/r8vnhill/dibs-astro"
```

but the source repository under review is `r8vnhill/dibs-astro-website` on GitLab.

That is not merely cosmetic once provenance/SBOM attestations are enabled: the image metadata itself describes the wrong
source.

**Recommendation:** make `SOURCE_URL` a non-secret build argument populated from GitLab's canonical project metadata and
use it for `org.opencontainers.image.source`. Do the same with version/revision metadata, then test the resulting OCI
configuration against expected CI values.

Also verify `org.opencontainers.image.licenses="BSD-2-Clause"` against the repository's authoritative license before
making it a publication contract; I would not silently assume that label is correct.

**Behavior:** metadata correction.

## P1 — CI does not enforce the runtime-hardening contract that local `test:container` claims

The local path in `scripts/test-container.mjs` is well structured: it starts the image read-only, provides `/tmp`
explicitly, checks the HTTP contract, verifies the configured user, and checks that Node, pnpm, source, `node_modules`,
and the npm credential file are absent. Cleanup is scoped to resources created by the test.

But when `CONTAINER_BASE_URL` is supplied—the CI path—the script returns immediately after the HTTP contract:

```text
CONTAINER_BASE_URL
      │
      ▼
waitForHttp
      │
      ▼
verifyHttpContract
      │
      ▼
exit
```

`verifyRuntimeContract()` never executes in CI.

So a future change could accidentally put Node or source code into the final image, or switch the configured user, and
the mandatory CI container jobs would not detect it.

**Recommendation:** split container assurance into explicit capabilities:

- **HTTP contract:** execute against the GitLab service.
- **Browser contract:** execute Playwright against that same candidate.
- **OCI image policy:** inspect the candidate manifest/config/filesystem without requiring a host Docker socket.
- **runtime execution policy:** keep the local `--read-only --tmpfs /tmp` test and, if the runner later supports an
  approved rootless runtime, execute it in CI too.

Do not introduce `/var/run/docker.sock` just to make all four concerns run in one implementation.

**Behavior:** assurance improvement.

## P1 — Invalid bibliography IDs are converted into misleading diagnostics

`normalizeReferenceId()` correctly rejects malformed IDs. But `resolveLessonReadings()` catches that error and
manufactures a branded `ReferenceId` anyway:

```ts
try {
    canonicalId = normalizeReferenceId(reading.referenceId);
} catch {
    canonicalId = `${REFERENCE_PREFIX}${reading.referenceId.trim()}` as ReferenceId;
}
```

The value then flows into duplicate or missing-reference detection.

This erases a meaningful distinction:

```text
malformed identifier
        ≠
valid identifier absent from catalog
```

It also undermines the purpose of the `ReferenceId` brand because a string that failed the constructor is immediately
cast into the branded type.

**Recommendation:** extend `LessonReadingDiagnostic` with an explicit format diagnostic, for example
`invalid-reference-id`, and stop processing that reading after normalization fails. Invalid IDs should never enter
`seen` and should never be queried against the bibliography catalog.

This is a particularly good DDT/PBT boundary:

- canonical ID remains unchanged;
- bare valid ID gains exactly one `ref:` prefix;
- invalid strings never construct a `ReferenceId`;
- normalization is idempotent for canonical IDs;
- duplicate detection operates only over normalized valid IDs.

This follows the guideline to make unsupported states difficult to construct and preserve precise machine-readable
diagnostics.

**Behavior:** diagnostic correctness change; successful valid configurations remain unchanged.

## P2 — The extracted `astro-icons` package still has an unclear ownership boundary

The project now consumes `@ravenhill/astro-icons@0.1.0` as an external dependency, and `packages/astro-icons` is no
longer a pnpm workspace.

However, the complete old `packages/astro-icons` source tree remains in the repository, and the new `$icons` facade
mixes two ownership models:

```ts
export * from "@ravenhill/astro-icons";

export { default as Bash } from "../packages/astro-icons/src/bash.svg";
export { default as Kotlin } from "../packages/astro-icons/src/kotlin.svg";
// ...
```

The facade itself is a good idea: UI code gets one stable import surface. The problem is that site-owned language assets
are still physically stored inside what looks like the source tree of the externally published package.

That makes ownership ambiguous for maintainers and makes it unnecessarily easy for the two repositories to drift.

**Recommendation:** keep `$icons`, but separate ownership physically:

```text
src/icons.ts
    ├─ re-export @ravenhill/astro-icons
    └─ export site assets from src/assets/icons/languages/
```

Then remove the residual package tree once all files that genuinely belong to the extracted package are confirmed to
live in its canonical repository.

Add an architecture regression test that site code cannot import from `packages/astro-icons/**`.

**Behavior:** behavior-preserving refactor.

## P2 — The readings data declares readonly contracts but retains a mutable inferred value

`LessonReadings` and `LessonReading` are declared using `Readonly` and readonly arrays, which is good. But
`libraryWhatIsReadings` uses:

```ts
const ... = { ... } satisfies LessonReadings;
```

rather than exposing the value itself as `LessonReadings` or as an `as const` value. The adapter then returns that
singleton directly.

`satisfies` checks compatibility without changing the inferred type into the readonly contract. The data object can
therefore retain more mutability in its inferred API than the declared model suggests.

**Recommendation:** expose the object through its declared immutable contract:

```ts
export const libraryWhatIsReadings: LessonReadings = {
    // ...
};
```

or use `as const satisfies LessonReadings` if preserving literals is useful.

I would not introduce runtime deep-freezing unless there is evidence of accidental mutation; type-level immutability is
sufficient here.

Also consider defining `LessonReadingGuide` from the same precise literal-union vocabulary rather than widening `type`,
`difficulty`, and `extent` back to generic `string` in the resolver. The data and resolver currently duplicate
overlapping concepts with different precision.

## P2 — The TypeScript 6 compatibility mechanism is more invasive than the current toolchain appears to require

The current root package already declares:

```text
typescript ^6.0.3
@typescript/typescript6 ^6.0.2
```

Yet `astro-check-typescript6-bridge.cjs` globally overrides Node's private `Module._resolveFilename` to redirect imports
of `typescript`, and `run-workspace-script.mjs` decides whether to inject that patch by looking for the substring
`"tsup"` in a package script.

The underlying compatibility concern is legitimate: TypeScript 7 currently does not expose the programmatic API required
by Astro and similar embedded-language tooling, and Microsoft recommends continuing with TypeScript 6 at those
boundaries. But Microsoft's supported transition mechanism is an npm alias when TS6 and TS7 need to coexist.
([Microsoft for Developers][3])

The current mechanism therefore has two smells:

- a private Node module-resolution hook;
- capability detection based on script text (`command.includes("tsup")`).

**Recommendation:** first characterize whether the bridge is still required now that `typescript` itself is TS6. If all
consumers pass without it, remove the bridge and the duplicate compatibility package. If a future TS7/TS6 split is
wanted, use the official package-alias model and explicit toolchain boundaries rather than monkey-patching resolution.

I would **not migrate Astro to TypeScript 7 now**; upstream explicitly says Astro still needs TypeScript 6 for these
programmatic-language-tooling paths. ([Microsoft for Developers][3])

## What I would keep

Several recent choices should survive the refactor:

- The static Astro artifact remains the correct boundary for both Cloudflare and OCI.
- The Dockerfile's multi-stage architecture, digest-pinned bases, frozen pnpm install, BuildKit secret mount,
  unprivileged NGINX runtime, and absence of Node from the final stage are good foundations.
- `test-container.mjs` has disciplined local resource ownership and cleanup.
- The presentation-facing readings bridge is consistent with the project's current architecture rules: UI is prohibited
  from reaching infrastructure directly, while presentation adapters are explicitly allowed to compose infrastructure.
- The recent introduction of toolchain checks and a machine-readable platform artifact manifest is well aligned with
  reproducible research-software practice.

I would improve those boundaries rather than replace them.

# Improvement plan

Because the findings span CI correctness, OCI provenance, package ownership, semantic contracts, and toolchain
compatibility, this is large enough for **milestones**, but I would keep them independently deliverable.

## Milestone 1 — Restore a trustworthy CI and container verification chain [DONE]

**Priority: required**

### Goal

Make every intended MR pipeline valid and ensure every container-specific check actually evaluates the OCI candidate it
claims to certify.

### Scope

Touch primarily:

```text
.gitlab-ci.yml
playwright.config.ts
scripts/test-container.mjs
container-related tests/configuration
```

### Cycle 1.1 — Make pipeline membership coherent

**Red:** use the current failed MR pipeline as the regression: mandatory `needs` dependencies cannot be instantiated.
([GitLab][1])

**Green:**

- establish `workflow: rules` for the supported pipeline kinds;
- reuse one consistent job-presence rule for required MR/branch/tag jobs;
- make `container:build`, HTTP contract, browser contract, and their consumers coexist in the same pipeline;
- do not make mandatory relationships `optional`.

**Refactor:** eliminate duplicated rule fragments using GitLab's reusable-rule facilities. GitLab explicitly supports
rule reuse and warns about mixing jobs with and without MR rules. ([GitLab Docs][2])

### Cycle 1.2 — Point Playwright at the candidate

**Red:** a configuration test demonstrates that `CONTAINER_BASE_URL=http://dibs:8080` still produces localhost as
Playwright's target.

**Green:** parameterize `baseURL` and disable `webServer` when an external deployment is provided.

**Refactor:** separate “test target selection” from general Playwright options if that keeps configuration simpler.

### Cycle 1.3 — Make OCI policy observable in CI

**Red:** characterize the current gap: HTTP CI mode succeeds without evaluating runtime-image policy.

**Green:** add daemon-independent OCI assertions for:

- configured user;
- OCI labels;
- forbidden project/build paths;
- absence of credential-bearing configuration.

Keep executable `--read-only` testing in environments that actually provide a suitable runtime.

### Acceptance criteria

- An MR pipeline is successfully created.
- Mandatory container jobs exist whenever downstream jobs need them.
- Browser tests access `dibs:8080`, not localhost.
- HTTP, browser, and image-policy checks are distinct and mandatory.
- Existing ordinary E2E behavior remains green.
- No Docker socket or privileged runner mode is introduced.

### Non-goals

- CI performance tuning;
- multi-platform images;
- vulnerability scanning;
- Cloudflare deployment changes.

## Milestone 2 — Make OCI publication evidence-based and provenance-correct [DONE]

**Priority: required**

### Goal

Guarantee that every durable OCI alias identifies the exact candidate that passed all container contracts.

### Scope

Restructure the container stage into:

```text
container:build
      │
      ▼
 candidate digest
   ┌──┼──────────────┐
   ▼  ▼              ▼
 HTTP browser   image policy
   └──┼──────────────┘
      ▼
container:publish
```

### Cycle 2.1 — Candidate-only build

**Red:** characterize that `container:build` currently creates durable aliases before verification.

**Green:**

- publish only a pipeline-scoped candidate;
- capture its immutable digest;
- export that digest as CI metadata/artifact.

### Cycle 2.2 — Promote rather than rebuild

**Green:**

After all candidate contracts succeed:

- `main` → SHA alias;
- release → SHA + canonical release aliases;
- all aliases reference the tested manifest digest.

No second application build should occur during promotion.

### Cycle 2.3 — Repair provenance metadata

Make OCI source/version/revision inputs explicit CI metadata.

Correct `org.opencontainers.image.source` to the canonical GitLab project rather than the current GitHub URL.

Add a small metadata-contract test so a future repository rename cannot silently leave stale provenance.

### Acceptance criteria

- Durable aliases cannot be published before candidate verification.
- Candidate digest == published digest.
- OCI source points to the actual project.
- Revision matches the Git commit.
- Provenance/SBOM describe the verified image.
- A failed contract leaves no new durable release alias.

### Non-goals

- image signing;
- vulnerability scanning;
- `latest`;
- additional registries.

## Milestone 4 — Make lesson-reading contracts semantically precise

**Priority: high-value**

### Goal

Make malformed, absent, and duplicated references distinct states and use one precise reading-domain vocabulary across
data and resolution.

### Cycle 4.1 — Preserve invalid-ID diagnostics

**Red:** add DDT cases for malformed IDs showing that they currently become `missing-reference` or
`duplicate-reference`.

**Green:**

Introduce:

```text
invalid-reference-id
missing-reference
duplicate-reference
```

as distinct diagnostic variants.

A failed normalization must never create a `ReferenceId`.

### Cycle 4.2 — Add properties for reference normalization

Use the already-present `fast-check` dependency rather than adding a new PBT library.

Useful properties:

- normalization is idempotent for canonical IDs;
- valid bare IDs get exactly one prefix;
- invalid syntax never returns the branded type;
- duplicate detection is invariant under bare/canonical spelling.

### Cycle 4.3 — Consolidate the reading model

Move the precise `type`, `difficulty`, and `extent` unions to the shared contract rather than widening those fields to
`string` in `LessonReadingGuide`.

Expose curated reading data under a readonly type.

Do not add runtime immutability machinery unless there is an actual mutation threat.

### Acceptance criteria

- Each diagnostic condition has one machine-readable code.
- Invalid identifiers never acquire the `ReferenceId` brand.
- All existing valid lesson reading pages render identically.
- One authoritative type vocabulary is used by configuration and resolver.
- Property tests cover normalization laws.

### Non-goals

- changing the reading curriculum;
- redesigning reading-page UI;
- moving bibliography storage.

## Milestone 5 — Simplify the TypeScript compatibility boundary

**Priority: high-value, after pipeline recovery**

### Goal

Retain Astro-compatible TypeScript 6 behavior with the smallest supported mechanism.

### Cycle 5.1 — Characterize tool requirements

Run independently:

- Astro check;
- each `tsup` workspace build;
- direct TypeScript checks;

with the compatibility bridge disabled.

Record which tool, if any, genuinely requires special resolution.

### Cycle 5.2 — Remove unnecessary global resolution patching

If the current `typescript ^6.0.3` satisfies all programmatic consumers, remove:

- `astro-check-typescript6-bridge.cjs`;
- conditional `NODE_OPTIONS` injection;
- redundant compatibility dependency if no longer required.

If the project intentionally adopts a TS7 CLI later, use the official TS6 alias strategy for tools needing the
programmatic API rather than overriding `Module._resolveFilename`. Microsoft currently recommends TS6 for Astro-style
embedded tooling. ([Microsoft for Developers][3])

### Cycle 5.3 — Make workspace orchestration capability-based

`run-workspace-script.mjs` should execute workspace scripts, not infer compiler requirements from the text `"tsup"`.

If compatibility-specific execution remains necessary, make it explicit in configuration or in the relevant workspace
command.

### Acceptance criteria

- Astro checking remains green on TypeScript 6.
- Workspace builds remain green.
- No private Node module-resolution API is used unless no supported mechanism can meet an evidenced requirement.
- Compatibility behavior does not depend on substring inspection of arbitrary shell commands.

### Non-goals

- forcing a TS7 migration;
- adopting experimental compiler features solely for novelty.

# Suggested execution order

I would implement the milestones in this order:

```text
1. CI graph
      ↓
2. Browser/container target
      ↓
3. Candidate → verify → publish OCI flow
      ↓
4. OCI provenance/runtime policy
      ↓
5. astro-icons ownership cleanup
      ↓
6. readings diagnostic/type strengthening
      ↓
7. TypeScript compatibility simplification
```

The **minimum useful vertical slice is Milestones 1–2**. At that point, the branch once again has a meaningful pipeline
and the OCI artifact is genuinely verified before publication. I would not merge the Docker delivery feature before that
slice is green.

The next most important architectural work is the icon ownership cleanup because the extraction is currently halfway
between an external package and an embedded source tree. The readings and TypeScript changes are worthwhile, but neither
should delay restoring CI correctness.

One additional research-software opportunity I would consider afterward is using the recently introduced
`platform-artifact-manifest` as the machine-readable oracle for both Cloudflare and OCI verification instead of
gradually accumulating hard-coded route samples in `test-container.mjs`. The repository already has a generator for that
semantic artifact. That would give DIBS a particularly clean contract:

```text
source
  ↓
dist + platform artifact manifest
  ├────────► Cloudflare
  └────────► OCI
               ↓
       same semantic contract
```

That is a better long-term direction than maintaining two independent deployment-specific notions of what a “correct
DIBS site” contains, and it directly supports the reproducibility and interoperability goals in the project guidelines.
