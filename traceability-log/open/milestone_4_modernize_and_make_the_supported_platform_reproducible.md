# Milestone 4 — Modernize and make the supported platform reproducible

## Goal

Move the repository to a coherent modern baseline:

```text
Node 24 LTS
pnpm 11
Astro 7
TypeScript 7
```

while preserving:

- static deployment;
- workspace topology and package boundaries;
- lesson and reference rendering semantics;
- generated-data contracts;
- navigation and browser behavior;
- PDF export;
- reusable-package public APIs and packed artifacts;
- deterministic/reproducible build inputs.

Each major ecosystem boundary must become green before the next is introduced.

Node 24 is an LTS line supported through April 2028, and pnpm 11 requires Node 22 or newer, so Node 24 is an appropriate
foundation for the rest of the migration. ([Node.js][1])

```mermaid
flowchart LR
    baseline[Characterized baseline]
    node[Node 24]
    pnpm10[pnpm 10 checkpoint]
    pnpm11[pnpm 11]
    astro6[Astro 6 / Vite 7]
    astro7[Astro 7 / Vite 8]
    ts6[TypeScript 6 bridge]
    ts7[TypeScript 7]
    release[Clean-checkout evidence]

    baseline --> node --> pnpm10 --> pnpm11
    pnpm11 --> astro6 --> astro7
    astro7 --> ts6 --> ts7 --> release
```

# Phase 4.0 — Freeze the pre-migration behavioral baseline

## Goal

Create enough evidence to distinguish genuine migration regressions from harmless serialization/tooling changes.

## Scope

Before changing versions, capture the current contracts for:

- clean dependency installation;
- workspace builds/checks;
- generated bibliography and lesson metadata;
- representative lesson render contracts;
- reference/readings rendering;
- architecture checks;
- static production build;
- browser E2E behavior;
- reusable package `build` / `pack` / `publint` / consumer checks;
- PDF smoke export.

The current root already centralizes most of these operations in scripts such as `check`, package-specific checks,
build, Astro tests, and PDF smoke export.

### Add a platform contract

Make `package.json` the canonical declaration for the intended runtime/package-manager baseline.

At minimum, introduce:

```json
{
    "engines": {
        "node": ">=24 <25"
    },
    "packageManager": "pnpm@<exact-version>"
}
```

Add one repository-owned version-manager file such as `.nvmrc` containing the exact validated Node 24 patch.

Do **not** introduce several equivalent version files merely to support every version manager.

Add a lightweight `check:toolchain` that verifies at execution time:

```text
Node major satisfies package.json#engines
pnpm version equals package.json#packageManager
```

This makes accidental local/CI drift visible.

### Differential baseline

Do not attempt to preserve every generated byte across Astro major versions. Instead derive a small semantic artifact
manifest containing stable facts such as:

```text
generated routes
lesson heading IDs
reference/citation targets
hydrated island identities
expected generated-data files
package exports
packed package file lists
```

Astro 7's new compiler can produce cosmetically different CSS serialization even when behavior is identical, so
whole-output byte comparisons would create misleading migration noise. ([Astro Docs][2])

## Acceptance criteria

- current branch is green before modernization;
- baseline failures are documented before any version changes;
- the semantic artifact manifest can be regenerated deterministically;
- exact starting versions are recorded;
- no dependency upgrade is mixed into this phase.

# Phase 4.1 — Move the runtime baseline to Node 24

## Goal

Make Node 24 the single supported development, CI, and build runtime before changing package-manager or framework
semantics.

## Scope

Update:

- `package.json#engines`;
- `.nvmrc` or equivalent;
- CI Node image/version;
- setup documentation.

Use an exact validated Node 24 LTS patch for reproducible local/CI builds. As of the current implementation window,
Node's current v24 line is LTS; resolve the exact patch at implementation time rather than hard-coding today's value
into this long-lived plan. ([Node.js][3])

### Important CI change

Do **not** defer CI runtime alignment to a later remediation task.

The current CI executes Node 20 and pnpm 9.15.9. An Astro 6+ migration cannot be meaningfully considered verified if
required CI still runs the former platform. Astro 6 itself requires Node 22.12 or newer. ([Astro Docs][4])

Changing:

```text
Node image/version
package-manager activation
```

is therefore in scope.

Changing:

```text
stages
runner ownership
cache architecture
deployment topology
```

remains out of scope.

## Verification

Run the complete baseline suite under Node 24 **while retaining the old pnpm/Astro/TypeScript versions**.

This isolation is important: any failure now belongs to the runtime boundary.

## Acceptance criteria

- local and CI runtime are Node 24;
- the preexisting dependency stack is green under Node 24;
- package consumer checks remain green;
- no Astro/pnpm/TypeScript major change is mixed into this phase.

# Phase 4.2 — Use pnpm 10 as an explicit migration checkpoint

## Goal

Avoid conflating two package-manager major migrations and provide a clean boundary from which the official pnpm 10→11
migration can be performed.

## Scope

Upgrade pnpm 9 → latest stable pnpm 10 first.

This need not become a long-lived supported platform; it is a migration checkpoint and should preferably be a distinct
commit/MR so regressions remain bisectable.

Regenerate the lockfile only with the pinned pnpm 10 version.

Verify:

- workspace membership;
- `node-linker=hoisted` behavior;
- peer resolution;
- registry access;
- lifecycle/build dependency behavior;
- reusable-package packed artifacts.

## Acceptance criteria

- frozen clean installation succeeds with pnpm 10;
- workspace resolution is unchanged;
- package tarball contracts remain unchanged;
- no framework dependency has been upgraded yet.

## Non-goals

- adopting pnpm 10 as the final supported package manager;
- unrelated dependency refreshes.

# Phase 4.3 — Migrate pnpm configuration and lockfile to pnpm 11

## Goal

Complete the package-manager migration using pnpm 11's configuration model rather than retaining compatibility-shaped
pnpm 9/10 settings.

## Scope

Upgrade from the pnpm 10 checkpoint to the latest stable pnpm 11 patch. At present, pnpm 11.20 is available and includes
additional package-resolution/security hardening, but the exact final patch should still be resolved at implementation
time. ([pnpm][5])

### Required configuration migration

This should be much more explicit than in the original plan.

Current `.npmrc` contains:

```text
auto-install-peers=true
node-linker=hoisted
lockfile=true
@ravenhill:registry=...
```

pnpm 11 only reads authentication and registry configuration from `.npmrc`; ordinary project settings now belong in
`pnpm-workspace.yaml`. ([pnpm][6])

Move the applicable settings to the workspace configuration using pnpm 11 names, for example conceptually:

```yaml
autoInstallPeers: true
nodeLinker: hoisted
```

Keep the registry declaration where supported.

### Consolidate lifecycle policy

The current workspace contains both:

```yaml
allowBuilds:
    ...

onlyBuiltDependencies:
    ...
```

pnpm 11 removes the legacy build-dependency settings in favor of `allowBuilds`; leaving both would encode two eras of
package-manager policy. ([pnpm][7])

Retain one canonical:

```yaml
allowBuilds:
```

contract and verify every permitted lifecycle dependency remains necessary.

### Security defaults

Do not automatically disable pnpm 11's stronger supply-chain defaults merely to mimic pnpm 9 behavior. pnpm 11 enables a
default package maturity window and stricter dependency-source behavior. ([pnpm][7])

Treat these as an intentional platform-policy improvement:

- keep them when compatible with the workflow;
- add narrowly scoped exceptions only with evidence;
- document exceptions and their reason.

### Verification

In addition to ordinary tests:

```text
delete node_modules
delete package-manager store/cache where useful for the reproducibility check
pnpm install --frozen-lockfile
```

Then run package build/pack/consumer checks from the fresh installation.

## Acceptance criteria

- exactly one pnpm 11 configuration model remains;
- `.npmrc` contains only configuration still supported there;
- `onlyBuiltDependencies` is gone;
- approved builds are represented by `allowBuilds`;
- clean frozen installation succeeds;
- no unreviewed lockfile drift remains;
- package artifacts remain consumer-compatible.

# Phase 4.4 — Upgrade Astro 5 → Astro 6 / Vite 7

## Goal

Reach a clean Astro 6 baseline while isolating all Vite 7, environment-model, syntax-highlighting, schema, and
integration changes from Astro 7.

Astro 6 moves to Vite 7, adopts Vite's Environment API internally, upgrades its internal Zod to 4, and upgrades Shiki
to 4. ([Astro Docs][4])

## Scope

Upgrade together:

- Astro;
- official Astro integrations;
- only those closely coupled dependencies required by the migration.

Use the official Astro upgrade tool as an **input to the migration**, not an unquestioned source of changes: inspect its
diff and retain only intentional changes. Astro recommends upgrading Astro and official integrations together.
([Astro Docs][2])

### First-class audit areas

#### Vite 7 / Environment API

Audit:

- `@tailwindcss/vite`;
- Paraglide integration;
- custom Vite/Astro integrations;
- Vitest configuration;
- dev/preview scripts;
- any direct Vite APIs.

The current Vitest version is 3.2.4; Astro 6's migration guide states that `getViteConfig()` requires at least Vitest
3.2, so this should be verified rather than upgraded automatically.

#### Zod 4

The root currently already declares Zod 4.3.6. Verify all Astro schema code against Astro 6's Zod 4 behavior and prefer
`astro/zod` where coupling to Astro's schema version is desirable.

#### Shiki 4

Make this a **required migration investigation**, not merely a generic dependency audit.

The repository currently directly depends on Shiki 3.9.1 and Shiki 3.x transformer packages, while Astro 6 upgrades its
syntax-highlighting stack to Shiki 4.

Exercise:

- `shiki-core`;
- code layouts;
- inline code;
- dual light/dark highlighting;
- PDF output.

### Differential testing

Compare Astro 5 and Astro 6 semantic artifact manifests.

Differences must be classified as:

```text
expected migration difference
or
unexpected regression
```

No unexplained drift.

## Acceptance criteria

- Astro 6 production build is green;
- browser suite is green;
- generated-data contracts are green;
- syntax highlighting is behaviorally equivalent;
- package consumer checks remain green;
- PDF smoke export remains valid;
- no Astro 7 changes are included.

# Phase 4.5 — Upgrade Astro 6 → Astro 7 / Vite 8

## Goal

Adopt Astro 7 while explicitly validating the compiler and routing changes that make this migration semantically
different from Astro 6.

Astro 7 upgrades to Vite 8 and makes the new Rust Astro compiler the sole compiler. ([Astro Docs][2])

## Scope

Upgrade Astro and official integrations together.

### Vite 8

Re-run the Vite-specific integration audit independently of the Astro 6 work. Astro's own guidance identifies direct
Vite plugins/configuration as the primary area requiring attention. ([Astro Docs][2])

### Rust compiler — required semantic validation

Astro 7's Rust compiler is stricter about invalid HTML and no longer silently restructures some invalid markup the way
the previous compiler did. It can also serialize CSS differently without changing rendering semantics. ([Astro Docs][2])

Therefore add explicit evidence for:

- nested lesson markup;
- callouts;
- lists;
- definition lists;
- code layouts;
- table structures;
- references/readings;
- rendered heading hierarchy.

Do not “fix” snapshot differences caused only by equivalent CSS serialization.

If recurring invalid HTML is discovered, evaluate a maintained HTML-validation tool as a separate evidence-based
dependency rather than creating a custom validator.

### Advanced routing

Astro 7 enables advanced routing by default and reserves `src/fetch.ts`. ([Astro Docs][2])

Audit:

```text
src/fetch.ts
routing configuration
redirect behavior
static route generation
```

If the project does not use advanced routing, explicitly decide whether to disable its fetch-file behavior rather than
silently accepting an unused new routing surface.

### Container/render-test APIs

Audit Astro Container API usage and integration-specific test renderers, since Astro 7 changes official integration
container-renderer entry points. ([Astro Docs][2])

## Acceptance criteria

- Astro 7/Vite 8 build is green;
- generated lesson HTML is semantically valid;
- all expected routes still exist;
- no unexpected hydration is introduced;
- browser E2E tests remain green;
- PDF path remains green;
- semantic artifact differences are fully classified.

# Phase 4.6 — Use TypeScript 6 as the migration bridge

## Goal

Eliminate TypeScript 6 deprecations and prepare configuration for TypeScript 7 **before** switching to the native
compiler.

This is the largest change I would make to the original TypeScript plan.

TypeScript's own guidance describes TypeScript 6 as the transition release for TypeScript 7 and recommends adopting it
first. TypeScript 7 turns several TypeScript 6 deprecations into hard errors. ([TypeScript][8])

## Scope

Upgrade 5.9 → 6 first.

### Required configuration audit

The current root config includes:

```json
"baseUrl": "."
```

TypeScript 7 no longer supports `baseUrl`; paths should instead be relative to the project root.
([Microsoft for Developers][9])

Because the current aliases already use relative targets such as:

```json
"~/*": ["./src/*"]
```

the migration may simply be able to remove `baseUrl`, but verify every workspace rather than assuming the root config
represents all packages.

Also audit:

- explicit `types`;
- `rootDir`;
- module/moduleResolution;
- deprecated compiler options;
- declaration output paths;
- JS checking behavior.

The root already declares an explicit `types` array and uses `moduleResolution: "Bundler"`, both of which reduce known
TypeScript 7 migration risk.

### Do not suppress migration diagnostics

Do not make:

```json
"ignoreDeprecations": "6.0"
```

part of the final bridge.

The target state for this phase is **TypeScript 6 with no compatibility suppression needed**, because TypeScript 7
removes those deprecated options entirely. ([TypeScript][8])

### Differential compiler evidence

Compare TypeScript 6:

- diagnostics;
- emitted declaration public surface;
- packed package type consumption;

against the TypeScript 5.9 baseline.

Do not require declaration files to be byte-identical if only stable ordering differs; compare public type contracts
instead.

## Acceptance criteria

- TypeScript 6 is green everywhere;
- no TS6 deprecation suppression remains;
- no `baseUrl` remains where TypeScript 7 would reject it;
- explicit `rootDir` is set wherever output shape depends on it;
- reusable packages expose the same public type contract.

# Phase 4.7 — Adopt TypeScript 7 as the canonical compiler

## Goal

Use TypeScript 7 for project compilation/type checking while isolating any temporary TypeScript 6 API compatibility
needs.

TypeScript 7 is now the native compiler and reports substantial build-speed improvements, but **7.0 intentionally ships
without the historical programmatic compiler API**. Microsoft provides `@typescript/typescript6` specifically for tools
that must temporarily run alongside TypeScript 7. ([Microsoft for Developers][9])

## Scope

Make TypeScript 7 the canonical:

```text
tsc
type-check
package type-contract
```

compiler.

### Refine the original “blocker” policy

Do **not** require every TypeScript 6 dependency to disappear merely to call this phase complete.

Distinguish:

```text
compiler use
    → must be TypeScript 7

compiler-API consumer
    → may temporarily use @typescript/typescript6
```

This side-by-side arrangement is an officially supported TypeScript 7.0 transition strategy, not necessarily evidence
that the migration is incomplete. ([Microsoft for Developers][9])

For every remaining TS6 compatibility dependency, record:

- consuming tool;
- why it needs the compiler API;
- exact package/version;
- scope;
- upstream migration issue/version;
- removal condition.

Do not let a compatibility alias leak across the whole workspace when only one package needs it.

### TypeScript 7 parallelism

Do not tune `--checkers` or `--builders` initially.

TypeScript 7 defaults to parallel checking and allows these values to be adjusted, but increasing concurrency trades CPU
for memory and can interact poorly with constrained CI runners. Measure first. ([Microsoft for Developers][9])

If CI resource use becomes problematic, pin an explicit checker count and document the evidence.

### Optional performance evidence

Record before/after:

```text
type-check wall time
peak memory if practical
CI elapsed time
```

on the same environment.

Treat these as modernization evidence, not correctness acceptance thresholds.

## Acceptance criteria

- normal project/compiler invocation resolves to TypeScript 7;
- Astro checks and workspace type checks are green;
- public declaration contracts remain compatible;
- any TS6 compatibility package is narrowly scoped and documented;
- no unsupported TS6 compiler option remains;
- no dependency remains on TypeScript 5.x.

# Phase 4.8 — Prove clean-checkout reproducibility and close the platform contract

## Goal

Demonstrate that the final platform works from source, not merely from an incrementally migrated working tree.

## Verification

From a clean checkout/cache-independent state:

```text
Node exact supported version
pnpm exact packageManager version
pnpm install --frozen-lockfile
pnpm check
pnpm test
browser E2E
pnpm build
reusable package pack/consumer checks
PDF smoke
```

Verify also:

- no tracked generated artifact drifts after canonical generation;
- semantic artifact manifest is stable;
- no unintended public package export changes;
- no route disappearance;
- no unexpected client hydration;
- PDF process cleanup still succeeds.

The current project has public reusable packages such as `@ravenhill/content-core` with `publint`, pack checking, and
packed-consumer checks, so these are important migration gates rather than optional post-upgrade checks.

## Documentation

Update:

- supported platform versions;
- installation/bootstrap instructions;
- package-manager activation;
- IDE/tooling expectations where TypeScript 7 differs;
- CI platform declaration;
- maintainer verification commands.

Traceability should record **each intermediate boundary**, not merely the final versions:

```text
Node old → Node 24
pnpm 9 → 10
pnpm 10 → 11
Astro 5 → 6
Astro 6 → 7
TS 5.9 → 6
TS 6 → 7
```

For each, record:

- version;
- required source/configuration changes;
- failures discovered;
- classification of output drift;
- test/build evidence.

# Assurance strategy

The guideline's broader verification techniques are relevant here, but not all provide equal value.

| Technique                      | Decision                                | Role                                                         |
| ------------------------------ | --------------------------------------- | ------------------------------------------------------------ |
| BDD/example tests              | **Required**                            | Existing rendering/domain regressions                        |
| DDT                            | **Required**                            | Route/lesson/component/package contract matrices             |
| Contract testing               | **Required**                            | Package exports, generated data, toolchain, rendering        |
| Differential testing           | **High value**                          | Semantic old/new output comparison at each major boundary    |
| Browser E2E                    | **Required**                            | Astro/Vite/client behavior                                   |
| Packed-consumer testing        | **Required**                            | Reusable package compatibility                               |
| Static analysis                | **Required**                            | Astro + TypeScript migration                                 |
| Clean-checkout reproducibility | **Required**                            | Lockfile/toolchain assurance                                 |
| PDF smoke                      | **Required at Astro boundaries/final**  | Export infrastructure                                        |
| Golden testing                 | **Limited**                             | Normalized semantic manifests only                           |
| PBT                            | **Reuse where already valuable**        | Domain logic, not platform-version testing                   |
| Metamorphic testing            | **No new platform-specific use needed** | Existing properties remain part of regression suite          |
| Mutation testing               | **Not a migration gate**                | Does not establish ecosystem compatibility                   |
| Fuzz testing                   | **Not selected**                        | No new parser/protocol boundary                              |
| Mock testing                   | **Avoid for platform behavior**         | Real builds/browser/package consumers give stronger evidence |
| Performance benchmarking       | **Optional/high value for TS7**         | Quantify modernization benefit                               |

## Explicit non-goals

This milestone does **not** include:

- SSR adoption;
- server endpoints;
- routing redesign;
- Astro Actions;
- new client hydration;
- visual redesign;
- workspace restructuring;
- package API redesign;
- migration to pnpm 12 while it remains a separate/newer platform decision;
- unrelated dependency refreshes;
- CI runner/topology redesign.

pnpm 12 is currently a separate Rust rewrite and is still documented as a release candidate, so keeping pnpm 11 as the
production target is a sensible stability boundary for this milestone. ([pnpm][10])

# Suggested execution order

```text
4.0  Freeze semantic/reproducibility baseline
 ↓
4.1  Node 24 only
 ↓
4.2  pnpm 9 → 10
 ↓
4.3  pnpm 10 → 11 + canonical config migration
 ↓
4.4  Astro 5 → 6 / Vite 7 / Shiki 4
 ↓
4.5  Astro 6 → 7 / Vite 8 / Rust compiler
 ↓
4.6  TypeScript 5.9 → 6; eliminate TS7-incompatible configuration
 ↓
4.7  TypeScript 6 → 7; isolate API compatibility packages
 ↓
4.8  Clean checkout + full artifact/release verification
```

The three changes I would consider **required corrections** to the original plan are therefore: **use pnpm 10 and
TypeScript 6 as diagnostic migration bridges; make pnpm 11's configuration-model changes explicit instead of merely
regenerating the lockfile; and distinguish TypeScript 7 compilation from TypeScript 6 compiler-API compatibility**. The
latter is especially important because TypeScript 7.0 deliberately does not provide the old compiler API, so “some
tooling still needs TypeScript 6” and “the project is still compiled with TypeScript 6” are no longer equivalent
statements. ([Microsoft for Developers][9])
