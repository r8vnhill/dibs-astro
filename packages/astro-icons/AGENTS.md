# Agent Guide: @ravenhill/astro-icons

## What is this package?

`@ravenhill/astro-icons` is a workspace package that holds 1,521 SVG icon files and exports them as Astro SVG
components. It is consumed by the Astro app via the `$icons` path alias.

## Directory structure

```
packages/astro-icons/
  src/
    index.ts               (auto-generated internal barrel; every repository-local icon)
    publishable.ts         (auto-generated publishable barrel; only release-approved icons)
    generated/
      internal/part-NNN.ts (sharded internal export modules, re-exported by index.ts)
      publishable/part-NNN.ts (sharded publishable modules, re-exported by publishable.ts)
    svg.d.ts              (module declaration for *.svg imports)
    acorn.svg
    address-book.svg
    … (1,519 more SVG files)
  dist/
    index.js              (generated by tsup from src/publishable.ts; SVG refs external)
    index.d.ts            (generated by tsup)
    index.js.map          (source map)
    *.svg                 (copied post-build; only publishable assets)
  migration/
    icon-inventory.json    (frozen, audited classification authority; never hand-edited)
  scripts/
    copy-assets.mjs               (post-build: copies only publishable src/*.svg to dist/)
    assert-pack-files.mjs         (validates tarball contents against the release-policy contract)
    verify-artifact-integrity.mjs (post-build: confirms every dist/index.js SVG import is packaged)
    audit-icons.mjs               (regenerates/checks the frozen migration/icon-inventory.json)
    lib/
      release-policy.mjs     (pure core: derives the publishable asset set, source/inventory drift,
                               and manifest vocabulary/duplicate findings)
      license-metadata.mjs   (pure: attribution manifest validation; shared vocabulary source)
      generate-exports.mjs   (pure: renders/shards generated export modules)
      artifact-integrity.mjs (pure: SVG import specifier vs. packaged-file resolution)
      publishable-plan.mjs   (imperative: resolves the audited release plan from the frozen
                               inventory + manifest, treating live src/*.svg only as drift evidence)
  package.json
  tsconfig.json
  tsup.config.ts
  README.md
  AGENTS.md (this file)
```

## Publication policy: source/internal availability is not permission to publish

This package intentionally exposes **two** export surfaces, both derived from the same frozen
icon inventory (`migration/icon-inventory.json`) and attribution manifest
(`LICENSES/third-party-icons.json`) through the single audited release plan resolved by
[`scripts/lib/publishable-plan.mjs`](./scripts/lib/publishable-plan.mjs) (imperative boundary)
over the pure core in [`scripts/lib/release-policy.mjs`](./scripts/lib/release-policy.mjs).
`migration/icon-inventory.json` is the classification authority: the live `src/*.svg` directory
listing is consulted only to detect **drift** against that frozen record (a file the inventory
expects but source is missing, or a source file the inventory does not track) -- it is never used
to (re)classify a file's group. An SVG dropped into `src/` without a corresponding audited
`migration/icon-inventory.json` entry blocks every publication-sensitive command (build,
`pack:check`, `generate-icons`) with an `releasePolicy.untrackedSource` finding until
`pnpm audit-icons:update` records it and its group.

- **Internal** (`src/index.ts`, consumed via the `$icons` alias): every repository-local icon,
  including custom assets whose release decision is `exclude`. A local SVG file existing in
  `src/` is not, by itself, a publication decision — the monorepo may keep using it.
- **Publishable** (`src/publishable.ts`, what `tsup` builds into `dist/index.js`, and what
  `copy-assets.mjs` copies into `dist/*.svg`): only assets the release policy currently approves:
  - every Phosphor-classified icon (the baseline), and
  - custom assets with `releaseDecision.action === "include"` **and**
    `redistribution.conclusion === "permitted"`.
  - `exclude` means the asset is absent from the standalone npm package, even though it stays
    available internally.
  - There is no `risk-accepted` override path. An asset marked `include` without permitted
    redistribution is a policy finding, not a publishable asset.

Neither the build (`tsup`, `copy-assets.mjs`) nor the pack-contract verifier
(`assert-pack-files.mjs`) independently reinterprets these rules — both consume
`derivePublishableIcons()`'s output. `pack:check` (real `npm pack --dry-run --json`, evaluated
through the same pure contract) is the authoritative artifact-level proof that the standalone
package matches the policy.

## Key implementation notes

### 1. Auto-generated export barrels

`src/index.ts` and `src/publishable.ts` are generated by `generate-icons-index.js` (at the
monorepo root), which shards exports into `src/generated/{internal,publishable}/part-NNN.ts` and
re-exports them via small `export *` barrels:

```ts
// src/index.ts
export * from "./generated/internal/part-001";
export * from "./generated/internal/part-002";
// …
```

```ts
// src/generated/internal/part-001.ts
export { default as Acorn } from "../../acorn.svg";
export { default as AddressBook } from "../../address-book.svg";
// …
```

**Do not edit any generated file manually.** To regenerate after adding/removing SVGs or changing
a release decision:

```sh
# From monorepo root
pnpm generate-icons
```

Regeneration throws if `derivePublishableIcons()` reports unresolved release-policy findings
(e.g. an `include` asset without permitted redistribution) — it never silently generates an
inconsistent barrel.

### 2. SVG type declaration

`src/svg.d.ts` declares `*.svg` imports as `AstroComponentFactory`:

```ts
declare module "*.svg" {
    const Component: import("astro").AstroComponentFactory;
    export default Component;
}
```

This is a standalone type declaration for this package. The Astro app's own `src/env.d.ts` has a similar declaration via
`/// <reference types="astro/client" />`, but the package needs its own so TypeScript can resolve SVG imports when
type-checking the barrel in isolation.

### 3. Build with external SVG imports

`tsup.config.ts` includes:

```ts
external: [/\.svg$/],
```

This tells esbuild to **keep SVG imports verbatim** in the output rather than trying to bundle them. The resulting
`dist/index.js` contains relative imports like:

```js
export { default as Acorn } from "./acorn.svg";
```

Vite (in the consuming Astro app) will then resolve these relative imports normally.

### 4. Post-build SVG copy

The build script runs two steps:

```json
"build": "tsup && node scripts/copy-assets.mjs"
```

`tsup` emits the publishable barrel but does not copy asset files. `copy-assets.mjs` runs after, resolving the current
publishable plan (`scripts/lib/publishable-plan.mjs`) and copying only those `src/*.svg` files to `dist/`, so the
published package contains the publishable barrel **and** exactly the release-approved SVG files.

### 5. Tarball validation

`scripts/assert-pack-files.mjs` validates package contents against the release-policy contract:

- Required files: `README.md`, `package.json`, `dist/index.js`, `dist/index.d.ts`, `dist/index.js.map`
- No source leak: `src/` is excluded (via `package.json` `files` field)
- No scripts leak: `scripts/`, `tsup.config.ts`, `tsconfig.json` excluded
- Exact SVG set parity: `dist/*.svg` in the tarball must equal the release-policy-derived publishable set exactly —
  both missing publishable assets and unexpected (non-publishable) packaged assets are reported by name. Equal counts
  with different filenames are treated as a failure, not a pass.

This is scale-invariant: no need to update the check when icons are added/removed, and it is policy-invariant: it
never silently accepts an excluded custom asset just because the counts happen to line up.

### 6. No consumer test script

Unlike other packages (e.g., `shiki-core`), there is no `scripts/validate-packed-consumer.mjs`. SVG transforms require
Astro's full build pipeline; a plain Node.js consumer cannot load SVG files. Instead, end-to-end validation is done in
Phase 5 by running the Astro dev server and production build.

## Common tasks

### Add or remove an icon SVG

1. Place the new `.svg` file in `src/` or remove an unwanted one
2. Run `pnpm --filter @ravenhill/astro-icons audit-icons:update` to regenerate the frozen
   `migration/icon-inventory.json` from the current `src/` contents. This is the classification
   authority; skipping it leaves the file untracked and every publication-sensitive command
   (`generate-icons`, `build`, `pack:check`) fails closed with a `releasePolicy.untrackedSource` /
   `releasePolicy.missingSource` finding.
3. Run `pnpm generate-icons` from the monorepo root
4. Both barrels (`src/index.ts` and `src/publishable.ts`, and their sharded `src/generated/*` parts) are regenerated
   automatically. A new custom asset only appears in `src/publishable.ts` once its manifest record has
   `releaseDecision.action: "include"` and `redistribution.conclusion: "permitted"`.
5. Commit the SVG, the updated `migration/icon-inventory.json`, and the regenerated barrels

### Add or change a non-Phosphor icon's attribution

Every non-Phosphor icon addition or change requires updating
[`LICENSES/third-party-icons.json`](LICENSES/third-party-icons.json) with a record that includes:

- the exact source URL for the asset;
- asset-specific terms (do not assume a software project's license covers its logos, trademarks, icons, or file-type
  marks — those are frequently governed by separate terms);
- a copyright conclusion;
- a trademark status;
- a redistribution conclusion;
- a release decision (e.g., include, exclude, or unresolved).

If any of these cannot be determined with confidence, record the record as unresolved and track the open question in the
traceability log. Do not treat unresolved or excluded assets as redistributable.

After changing the manifest, regenerate and check the generated notices:

```powershell
pnpm --filter @ravenhill/astro-icons test:licenses
pnpm --filter @ravenhill/astro-icons licenses:update
pnpm --filter @ravenhill/astro-icons licenses:check
```

`licenses:update` regenerates [`LICENSES/THIRD_PARTY.md`](LICENSES/THIRD_PARTY.md) from the manifest; never hand-edit
that file.

The publishable-artifact contract is enforced by `pack:check` before an included asset can ship:

- `releaseDecision.action: "include"` requires `redistribution.conclusion: "permitted"`;
- an included asset's `licenseFile`, `permissionFile`, and `policyFile` references must be present in the artifact;
- development-only paths such as `migration/` remain blocked;
- there is no `risk-accepted` override.

The checker enforces recorded repository policy and package integrity; it does not determine legal rights. Any future
exception requires an explicit policy and traceability decision rather than an ad hoc enum extension.

### Rebuild the package

```sh
pnpm --filter @ravenhill/astro-icons build
```

Check that `dist/` contains:

- `index.js`, `index.d.ts`, `index.js.map`
- only publishable `.svg` files (currently 1,512 — every Phosphor icon; none of the 9 currently-excluded custom
  assets), not the full `src/` count

### Validate the package

```sh
pnpm --filter @ravenhill/astro-icons check
```

This runs, in order: policy/build unit tests (`test:audit-icons`), licensing tests
(`test:licenses`), pack-contract tests (`test:pack-files`), generated license-notice freshness
(`licenses:check`), generated export-surface freshness (`generate-icons:check`), the build,
typecheck, the real-artifact pack contract (`pack:check`), the built-module SVG import integrity
check (`verify:artifact-integrity`), and finally `lint`. `pack:check` and the artifact integrity
check run before `lint` so a `publint` tooling hiccup never blocks collecting package-contract
evidence.

### Test package publication

```sh
pnpm --filter @ravenhill/astro-icons pack:dry-run
```

This creates a fake tarball and lists its contents without publishing.

## When to contact humans

- **If barrel generation fails**: Check that `generate-icons-index.js` paths are correct and `src/*.svg` files exist.
  A release-policy error (unresolved manifest findings) also fails generation on purpose — see "Publication policy"
  above.
- **If pack validation fails**: Check that `dist/` was populated after build (`copy-assets.mjs` ran), and read the
  reported `missingAssets`/`unexpectedAssets` — they name the exact filenames that differ from the release-policy-
  derived publishable set.
- **If the Astro app can't find icons**: Check that `$icons` alias in root `tsconfig.json` points to
  `./packages/astro-icons/src/index.ts`.
- **If icons don't render in the browser**: The issue is likely in the Astro app's SVG pipeline, not in this package.
